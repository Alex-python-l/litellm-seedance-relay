# 企业中转站测试计划

> 适用范围：企业账户、登录与激活、API Key、管理员额度调整、价格版本、通用模型请求计费、Seedance 视频任务、门户与管理后台、数据库迁移、备份恢复和后台清理任务。
>
> 金额统一使用整数微美元（`micros`）：`1 USD = 1,000,000 micros`。测试代码、接口和数据库断言都不得使用浮点数比较金额。

## 1. 目标与当前边界

本计划的目标是证明以下四件事：

1. 任何请求都不能把企业钱包扣成负数，也不能重复扣款、重复充值或跨企业读取数据。
2. 每一次额度变化都能由不可重复的账本记录解释，并能从请求、价格版本和实际用量追溯。
3. 激活、重置密码、登录、API Key 和管理员操作在失败时不会留下部分数据或泄露敏感信息。
4. 发布、迁移、备份和恢复不会破坏余额、预占、账本及视频任务的一致性。

### 1.1 “支付”在当前版本中的含义

当前版本不是在线收款系统。已实现的是：管理员人工增加或扣减企业额度，请求开始时预占额度，完成后按实际用量结算，失败时释放预占。

以下面向消费者的能力当前必须保持不可用：

- 用户自助注册；
- Stripe Checkout；
- Stripe webhook；
- 支付单退款接口。

因此，`/v1/public/auth/register`、`/v1/public/payments/stripe/webhook`、`/v1/portal/billing/checkout` 和 `/v1/admin/relay/payments/{payment_id}/refund` 被暴露时应判定为安全回归。`stripe_client.py` 目前也不构成可用的支付实现。

如果未来接入真实支付，必须先通过第 12 节的支付上线门禁，不得把“管理员调额通过”视为“在线支付通过”。

## 2. 风险等级与放行规则

| 等级 | 定义                                                 | 示例                                             | 放行规则                               |
| ---- | ---------------------------------------------------- | ------------------------------------------------ | -------------------------------------- |
| P0   | 直接造成资金错误、越权、密钥泄露或不可恢复的数据损坏 | 重复扣费、重复充值、跨企业读取、明文保存上游 Key | 必须自动化；任何失败立即阻断发布       |
| P1   | 核心业务不可用或账务无法追溯                         | 激活失败、视频任务不结算、价格版本错误           | 必须通过；不可用例须有负责人和明确豁免 |
| P2   | 管理体验、展示或非核心恢复能力异常                   | 复制按钮、分页、错误提示                         | 不阻断紧急回滚，但必须进入修复计划     |

发布必须同时满足：

- 所有 P0、P1 用例通过；
- 数据库迁移前进和回滚演练通过；
- 备份恢复后的财务不变量通过；
- 测试证据中不包含密码、完整 API Key、会话 Cookie 或上游 Key；
- 生产冒烟只执行只读操作，或执行经过明确授权、可逆且有独立幂等键的调额操作。

## 3. 财务与隔离不变量

以下是不依赖界面文案的最终断言，是财务类测试的测试预言（oracle）。设操作前钱包为：可用额度 `A`、预占额度 `R`，本次预占 `Q`、实际收费 `C`、人工调整 `D`。

### 3.1 钱包不变量

- 任意提交后：`available_micros >= 0` 且 `reserved_micros >= 0`。
- 预占成功：`A' = A - Q`，`R' = R + Q`，所以 `A' + R' = A + R`。
- 请求结算：`0 <= C <= Q`，`A'' = A - C`，`R'' = R`。
- 请求释放：`A'' = A`，`R'' = R`。
- 人工调整：`A' = A + D`，`R' = R`；若 `A + D < 0`，整个事务必须失败且钱包与账本均不变。
- `version` 每次真实钱包写入只增加 1；幂等重放不得增加版本。

### 3.2 账本与请求不变量

- 一个 `request_id` 最多有一个预占、一个实际收费记录。
- 一个 `idempotency_key` 最多有一个账本条目。
- 预占账本为 `RESERVE`，结算差额为 `RELEASE`，最终收费为 `USAGE`，人工调额为 `ADJUSTMENT`。
- `USAGE.amount_micros = -charged_micros`。
- 每条账本的 `available_after_micros`、`reserved_after_micros` 必须等于该事务提交后的钱包快照。
- 请求结算必须使用预占时保存的 `price_id`；后续发布新价格不得改变旧请求费用。
- 同一请求再次结算或释放不得改变钱包、账本条数和收费条数。
- 所有门户查询必须按 `account_id` 隔离；资源属于其他企业时返回 404，不返回“存在但无权限”之类的可枚举信息。

### 3.3 金额计算不变量

- 单类 Token 费用：`ceil(tokens * rate_micros_per_million / 1,000,000)`。
- 缓存输入 Token 最大只能等于输入 Token；超出的部分按输入 Token 计费规则处理。
- 输入、输出、缓存输入和价格不得为负数。
- 嵌入请求只使用嵌入价格；普通生成请求按输入、缓存输入和输出分别计算。
- 金额展示只能由整数 `micros` 格式化，不能从二进制浮点数反推账务值。

## 4. 测试分层与环境

| 层级       | 环境                                    | 主要目标                                   | 是否允许真实上游             |
| ---------- | --------------------------------------- | ------------------------------------------ | ---------------------------- |
| 单元测试   | 本地，无数据库                          | 金额计算、密码策略、序列化、路由分类       | 否                           |
| 数据库集成 | 独立 PostgreSQL，每例回滚或重建 schema  | 行锁、事务、幂等、唯一约束、迁移           | 否                           |
| API 集成   | 本地 LiteLLM + 独立 PostgreSQL + 上游桩 | HTTP 状态、错误码、Cookie、CSRF、计费链路  | 仅桩服务                     |
| 浏览器 E2E | 预发布环境                              | 激活、登录、复制、调额、重置密码、数据同步 | 默认桩服务                   |
| 上游契约   | 预发布环境 + 专用低额度供应商 Key       | Seedance 请求和状态结构兼容性              | 是，受控执行                 |
| 生产冒烟   | 生产环境                                | 健康检查、只读查询、隔离验证               | 不创建付费任务，除非单独授权 |

测试环境必须满足：

- 使用与生产相同大版本的 PostgreSQL；
- 固定时区为 UTC，界面再按浏览器时区展示；
- 每个测试运行生成唯一 `run_id`，企业邮箱、请求 ID 和幂等键均包含该值；
- 上游桩能模拟成功、超时、429、4xx、5xx、畸形 JSON、无 usage、延迟完成和重复回调；
- 并发测试至少使用两个独立数据库连接，不能用同一事务伪装并发；
- 测试后删除或失效测试 API Key，不在日志和报告中保存完整凭证。

## 5. 断言规范

### 5.1 每个 API 用例至少断言四层

1. HTTP：精确状态码、响应类型和稳定的机器错误码；不要只断言文案包含某个词。
2. 业务：响应中的企业、钱包、任务、价格版本与请求输入一致。
3. 数据库：受影响行数、金额变化、状态、唯一键和快照值精确相等。
4. 副作用：未创建多余账本、未重复调用上游、未发送多封邮件、日志未出现秘密。

推荐写法：

```python
assert response.status_code == 402
body = response.json()
assert body["error"]["code"] == "insufficient_balance"

wallet_after = await load_wallet(account_id)
assert wallet_after.available_micros == wallet_before.available_micros
assert wallet_after.reserved_micros == wallet_before.reserved_micros
assert await count_ledger(wallet_id) == ledger_count_before
assert await count_open_reservations(account_id) == reservations_before
assert upstream.calls == 0
```

金额成功路径推荐写法：

```python
expected_charge = (tokens * rate + 999_999) // 1_000_000
assert charge.charged_micros == expected_charge
assert wallet_after.available_micros == wallet_before.available_micros - expected_charge
assert wallet_after.reserved_micros == wallet_before.reserved_micros
assert usage_entry.amount_micros == -expected_charge
assert usage_entry.available_after_micros == wallet_after.available_micros
assert usage_entry.reserved_after_micros == wallet_after.reserved_micros
```

幂等测试必须比较第一次操作后的完整快照：

```python
first = await snapshot_finance_state(account_id)
second_response = await repeat_same_request()
second = await snapshot_finance_state(account_id)

assert second_response.status_code == first_response.status_code
assert second == first
assert upstream.calls == 1
```

### 5.2 禁止使用的弱断言

- `assert response.status_code < 500`：400、401、402、403、404 的语义完全不同。
- `assert balance > 0`：不能证明金额计算和一次性扣款正确。
- `pytest.approx()` 比较 `micros`：金额必须整数精确相等。
- 只看界面 toast：必须同时核对接口响应和数据库状态。
- 只断言有一条日志：必须核对它属于正确企业、请求、价格版本和金额。
- 用 `sleep()` 等待过期：应注入时钟或直接设置数据库时间，避免不稳定测试。

### 5.3 数据库快照建议

财务测试前后至少读取：

- 钱包：`available_micros`、`reserved_micros`、`version`；
- 预占：`request_id`、`price_id`、`reserved_micros`、`status`；
- 收费：Token 数、`charged_micros`、`upstream_cost_micros`；
- 账本：类型、金额、两个 after 快照、幂等键和请求 ID；
- 视频任务：企业、请求、上游任务 ID、估算/实际 Token、收费和状态。

不要用测试 SQL 直接修改钱包后再验证业务流程；准备余额必须通过创建企业或管理员调额接口，只有专门验证数据库约束的用例可以直接写表。

### 6.6 通用模型请求的预占、结算与释放

| ID       | 等级 | 场景                                     | 关键断言                                                                                    |
| -------- | ---- | ---------------------------------------- | ------------------------------------------------------------------------------------------- |
| BILL-001 | P0   | 余额大于、等于、少于报价 1 micros        | 前两者成功预占；少 1 返回 402 `insufficient_balance` 且不上游                               |
| BILL-002 | P0   | 客户伪造 request ID                      | 服务端生成新 ID；客户值不能覆盖收费和账本关联键                                             |
| BILL-003 | P0   | 同一 request ID 重放                     | 返回原预占；钱包和 `RESERVE` 条数不变                                                       |
| BILL-004 | P0   | 预占成功                                 | `A-Q`、`R+Q`、版本 +1、唯一预占和账本快照均精确匹配                                         |
| BILL-005 | P0   | 成功且实际费用小于预占                   | 收费 `C`，释放 `Q-C`；最终 `A-C`、`R`；收费/usage 各一条                                    |
| BILL-006 | P0   | 实际费用恰好等于预占                     | 无多余 `RELEASE`；最终只减少 `C`                                                            |

## 7. 必测边界值集合

参数化测试至少覆盖以下集合：

- 金额：`-1, 0, 1, 999_999, 1_000_000, 1_000_001`；接近 BIGINT 上限的值单独执行。
- Token：`-1, 0, 1, 999_999, 1_000_000, 1_000_001`。
- 余额与报价差：`balance = quote - 1`、`quote`、`quote + 1`。
- 密码长度：`11, 12, 128, 129`，并分别缺少大写、小写、数字。
- 文本字段：空字符串、纯空白、最短合法、最大合法、最大加 1、Unicode、emoji、HTML/脚本片段。
- 列表：`0, 1, limit - 1, limit, limit + 1`，并构造相同 `created_at`。
- 时间：`expires_at - 1 microsecond`、`expires_at`、`expires_at + 1 microsecond`。
- 并发：同请求同载荷、同请求不同载荷、不同请求同钱包、不同企业相同客户端幂等键。
- 上游：200 成功、202 处理中、400、401、404、409、429、500、502、超时、断连、空响应、非 JSON、字段缺失。

边界用例不能只验证接口不崩溃；每个失败边界都要断言“所有财务表和外部调用均无副作用”。

## 8. 端到端关键旅程

### E2E-01：企业首次开通并成功使用 Seedance

1. 管理员创建初始额度为 1 USD 的企业。
2. 企业通过一次性激活链接设置合规密码并登录。
3. 企业创建 API Key，刷新页面后确认完整 Key 不再显示。
4. 使用 Key 创建 Seedance 任务，记录 `request_id`、`task_id` 和预占。
5. 上游桩把任务从 processing 变为 succeeded 并返回实际 Token。
6. 门户查看钱包、账本、用量、日志和视频任务；管理后台查看同一任务。

最终断言：企业与管理员看到的任务核心字段一致；企业余额只减少实际费用；预占归零；一条收费记录；无跨企业数据；完整 API Key 和供应商 Key 未出现在任何页面或日志。

### E2E-02：余额不足

把企业余额调到比报价少 1 micros，提交任务。必须返回 402 `insufficient_balance`，上游调用数为 0，视频任务、预占、收费和账本条数均不变。

### E2E-03：上游失败与恢复

先让创建成功并保持 processing，再模拟上游失败或超时。前台查询和后台协调并发运行，最终只能得到一个失败终态，预占完整释放，重复轮询不改变任何财务快照。

### E2E-04：调额幂等与审计

管理员对同一钱包发送 20 个并发的同幂等键充值请求。最终只增加一次，账本只新增一条，版本只增加一次；随后用不同幂等键扣减到恰好 0 成功，再扣 1 micros 失败且完全回滚。

### E2E-05：跨租户隔离

企业 A、B 各创建 Key 和任务。用 A 的会话/API Key 遍历 B 的 Key ID、task ID、request ID 及分页游标。所有直接资源访问返回 404，列表中不出现 B 数据，上游也不因越权查询被调用。

## 9. 自动化现状与缺口

当前已有自动化覆盖：

- 金额向上取整、缓存输入、嵌入计费和金额展示；
- 密码哈希、邮箱规范化、秘密的域隔离；
- 价格结构、路由白名单和服务端请求 ID；
- Seedance 估算、上游鉴权、幂等、租户隔离、成功结算与失败释放；
- 当前消费者支付路由保持不存在；
- 内容加密和基础配置校验；
- 管理后台调额 SQL 字段和密码重置反馈的 UI 回归。

发布真实资金功能前必须补齐的自动化缺口：

1. 使用真实 PostgreSQL 的预占/结算/释放/调额并发事务测试；
2. 钱包和账本重放校验器；
3. 激活、重置、会话、CSRF 和限流的完整 API 集成测试；
4. 浏览器端激活、重置、复制、调额和列表同步 E2E；
5. 数据库迁移、备份恢复和恢复后财务重算；
6. BIGINT 上限前的 API 校验；
7. 同一调额幂等键被改金额或改钱包复用时的冲突校验；
8. 实际费用超过预占时的商业策略、告警和测试。

缺口列表是放行依据的一部分。未自动化的 P0 用例即使人工通过，也必须记录临时豁免、证据、责任人和到期时间。

## 10. 建议的 CI 执行顺序

在仓库根目录运行：

```bash
# 快速单元与契约测试
python -m pytest tests/test_litellm/proxy/public_relay -q

# 管理后台回归测试
cd ui/litellm-dashboard
npx vitest run src/components/public-relay/RelayAdmin.test.tsx
npx prettier --check src/components/public-relay
npx eslint src/components/public-relay

# UI 生产构建
npm run build
```

CI 建议拆为四个必须通过的检查：

1. `public-relay-unit`：纯单元和路由契约；
2. `public-relay-postgres`：迁移、事务、幂等、并发和财务不变量；
3. `public-relay-ui`：组件测试、格式、静态检查和生产构建；
4. `public-relay-e2e`：本地网关、PostgreSQL、上游桩和浏览器关键旅程。

真实 Seedance 契约测试应是受保护的手动工作流，使用低额度专用 Key，不在普通 PR 上自动消耗供应商余额。

## 12. 未来真实支付上线门禁

真实收款接入后，需要新增独立的 Payment、PaymentEvent、Refund 等不可变记录，充值只能由服务端验证后的支付事件驱动，不能信任浏览器提交的金额。以下 P0 用例全部自动化通过之前，不得开放支付入口：

| ID      | 场景                               | 必须断言                                                         |
| ------- | ---------------------------------- | ---------------------------------------------------------------- |
| PAY-001 | webhook 签名正确/错误/缺失         | 只有正确签名进入业务；失败无订单和账本副作用                     |
| PAY-002 | 同一事件重复 2 次、20 次及并发重复 | 只入账一次；返回供应商要求的幂等响应                             |
| PAY-003 | 事件乱序                           | 支付成功、退款、拒付按状态机收敛，不因旧事件覆盖新终态           |
| PAY-004 | 金额、币种、商户、订单或客户不匹配 | 拒绝入账并告警；绝不采用客户端金额                               |
| PAY-005 | Checkout 过期、取消、支付中        | 不提前充值；前端刷新不能伪造成功                                 |
| PAY-006 | 全额、部分、多次部分退款           | 退款总额不超过实收；额度和退款账本精确匹配                       |
| PAY-007 | 退款时可用额度不足                 | 按明确策略进入欠款/冻结/人工处理，不能把现有非负钱包约束打穿     |
| PAY-008 | 拒付和撤销                         | 状态、额度、账户限制和审计记录一致，重复事件不重复扣减           |
| PAY-009 | webhook 处理到一半崩溃             | 数据库事务回滚；重试后恰好执行一次                               |
| PAY-010 | 供应商 API 超时但实际已支付        | 通过事件/查询幂等收敛，不能因客户端重试重复创建充值              |
| PAY-011 | 测试/生产环境混用                  | 环境、商户和签名密钥不匹配即拒绝；生产不接受测试事件             |
| PAY-012 | 对账                               | 支付商实收、退款、内部支付记录和额度账本逐日可对平，差异自动告警 |
| PAY-013 | 权限与审计                         | 退款/人工修正需管理员权限、原因、幂等键和不可修改审计记录        |
| PAY-014 | 数据保护                           | 卡数据不进入本系统；日志、错误、监控和测试证据均无支付秘密       |

真实支付发布还必须完成小额实付、小额退款、对账、故障回放和密钥轮换演练，并由开发之外的第二人复核财务证据。
